# §6.23 Post, report and change brief: getting a review out of GraphReview

Status: **built 2026-10-17.** Three ways to take a review somewhere else, all
user-triggered: post the picked findings to the PR/MR as a review, export
the whole review as a Markdown report, and generate a change brief (release
notes for a ref range).

## 1. Post review to the PR/MR

Locked decision #10 says the review never *auto*-posts. Posting is therefore
only ever the user's click, after a preview, and nothing posts on a schedule,
on review completion or from the chat.

- **Where.** The review dock's ⋯ menu → *Post review to GitHub/GitLab…*,
  shown only for a PR target on a repo linked to GitHub or GitLab. A ref
  comparison has no PR, so the item isn't there.
- **The dialog.** `GET /api/repos/[repoId]/review/post?prNumber=` returns a
  draft: one row per finding with a file location, each with the inline
  comment it would become (file, line, body) or why it can't be inline,
  plus a summary body and the post history. The user ticks findings
  (default: open defects and concerns not posted yet), edits the summary
  and picks a verdict — **Comment**, **Approve** or **Request changes** —
  then *Post review*.
- **Inline or in the summary.** A finding's `lineRange` (`"12"` or `"12-40"`)
  becomes an inline comment only when its end line is an added or context
  line of the file's diff at the head (`lib/review-post/hunks.ts` reads the
  patch). Otherwise — a caller the change didn't touch, a deleted file, a
  line outside the hunks — it goes into the summary as a `file:line — …`
  bullet, so the host never rejects the whole review over one line. The
  dialog shows which is which.
- **GitHub.** One call: `POST /repos/{o}/{r}/pulls/{n}/reviews` with
  `commit_id` (the head the draft was built from), `event`
  (`COMMENT | APPROVE | REQUEST_CHANGES`), `body` and `comments[]`
  (`path`, `line`, `side: "RIGHT"`, `start_line`/`start_side` for a range in
  one hunk). GitHub refuses Approve and Request changes on your own PR; that
  error is shown as is.
- **GitLab.** One discussion per inline comment
  (`POST …/merge_requests/:iid/discussions` with a `text` position built from
  the MR's `diff_refs`), then the summary as a note. Verdicts: Approve →
  `POST …/approve`. GitLab's REST API has no "request changes" state, so
  **Request changes** posts the summary headed *Changes requested* and
  revokes your approval (`POST …/unapprove`, a 404 meaning "you hadn't
  approved" is fine) — the closest equivalent. Comment touches approvals not
  at all. Discussions are posted one by one; if one fails midway, the ones
  already posted are recorded, so a retry doesn't duplicate them.
- **Token scopes.** Checked before posting. GitHub classic PAT: the
  `x-oauth-scopes` header must hold `repo` (or `public_repo` for a public
  repo). A fine-grained PAT has no such header; it needs *Pull requests:
  Read and write*, and a 403/404 from the post is reported as exactly that.
  GitLab: `GET /personal_access_tokens/self` must list `api` (`read_api` can't
  write). A missing scope is an error naming the scope, before anything is
  sent.
- **No double posting.** Every posted finding is recorded in `kv`
  (`posted-review:<repoId>:<targetKey>`) by id *and* by fingerprint
  (category, file, line, summary), with the time and the comment's URL, plus
  one entry per review posted. A re-run of the review writes new finding ids
  but the same fingerprints, so a finding posted before stays posted. The
  server refuses (409) a post that includes an already-posted finding, and a
  per-target lock refuses a second post while one is in flight. The dialog
  shows posted findings ticked off with a link to their comment.

## 2. Full Markdown report

`GET /api/repos/[repoId]/review/report?prNumber=|baseRef=&headRef=` builds
the report on the server (`lib/review-post/report.ts`) from what's already
stored — no model call, no clone. It is a list of sections,
`REPORT_SECTIONS`, each `{ id, title, render(ctx) }` returning Markdown lines
or `null` to leave itself out:

1. header — target, PR title and link, reviewed head, overall verdict;
2. intent — the PR-level "delivers what it describes" verdict and why;
3. findings — open (worst first, with a clipped rationale), resolved, counts;
4. impact — callers left behind, grouped by the changed declaration;
5. checklist — every item's status (evaluated without AI, as the panel does);
6. API, 7. infra, 8. schema, 9. env — the catalog diffs from the target graph;
10. previews — each completed before/after preview: cases run, cases that
    differ, errors.

Adding a section (the Tests view's AI test plan, for one) is one entry in
`REPORT_SECTIONS`; `render` may be async and load its own data from `ctx`.
The dock's ⋯ menu → *Export report…* shows it with **Copy** and **Download
.md**.

## 3. Change brief

`GET|POST /api/repos/[repoId]/review/brief`. Four lists — **user-visible
changes**, **contract changes** (API, schema, env, infra; breaking API
changes first), **risks** and **open questions** — plus a one-line summary.
Built from what the tool has: the PR title/description, the intent verdict,
the catalog diffs, open findings, unmentioned changes (questions: "was this
meant to be in here?") and impact callers.

- GET returns the last brief generated for this head, else the
  deterministic one (`lib/review-post/brief.ts`), built with no model.
- POST makes one AI call (`lib/ai/change-brief.ts`, `TASK: change-brief`,
  answered by the mock server) that rewrites those facts into the four
  lists; with no provider configured, or when the answer can't be read, the
  deterministic brief is returned with a note. The result is cached in `kv`
  per target and head.
- It copies or downloads as Markdown. For a ref range it is titled
  **Release notes** (`base…head`) instead of *Change brief*.

Both exports live in the same dialog (*Export report…*), as two tabs.
