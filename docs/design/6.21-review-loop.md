### 6.21 Review loop: stable findings, incremental re-review, suppression memory (built 2026-10-17)

The 7-persona review (2026-10-17) picked this as the first fix. A re-review threw every finding away: "change" findings got fresh random ids, so a reviewer's resolve, re-rate and replies, and the chat's triage records pointing at a finding, were lost on every run. Each push meant paying for every component again. A finding dismissed as noise came back on the next review. This section closes that loop.

#### 1. Stable finding ids

A `change` finding's id is derived from what it is about: `chg-` plus a sha256 of repo, target key, component, file and the **normalized summary** (lower case, punctuation, pure-number words such as line numbers, and stopwords dropped; identifiers kept; `changeFindingId`, `lib/db/review-loop.ts`). The id the review job passes in is ignored.

The review job writes each component's findings through `syncFindingsForTargetComponent` (`lib/db/finding.ts`), not the old delete-and-insert:
- A finding with the same derived id is the same finding.
- Otherwise it adopts the id of the closest unclaimed stored finding **on the same file** when the word-set (Jaccard) similarity of the normalized summaries is at least `CARRY_OVER_SIMILARITY` (0.6). The model rarely words a point the same way twice. Exact ids are claimed before fuzzy ones.
- A recognised finding keeps `createdAt`, `resolvedAt`, `responses` and `reratedTo`. `reratedTo` is new: `rateFinding` sets it, and it overrides the model's new verdict. An OK verdict drops `resolvedAt`.
- Stored findings nobody claimed are deleted. Two findings that say the same thing about the same file get `-2`, `-3` suffixes.

Chat triage records (`ChatTriageRecord.findingId`) need no change: the id they hold survives.

#### 2. Incremental re-review

Migration 8 adds `review_slots (repo_id, target_key, component_id, patch_hash, head_sha, reviewed_at)`: what each component's last successful call saw. `patch_hash` is a sha256 of the model, the effort, and each changed file's path, status and patch, sorted by path. Hunk headers are included, so shifted lines count as a change. A file with no diff text (binary, too big) makes the component never reusable. Related-code context is deliberately left out of the hash.

When a review runs (not "Retry failed") and a component's slot has a **different head** but the **same hash**, and the component has no failed-call placeholder, no call is made. Its findings are restamped with the new head and revision, the slot moves to the new head, and its summaries still feed the impact, intent and PR map passes. A re-run at the **same head** asks every component again: that is a deliberate "ask again". A failed call deletes its slot, and the slots of components the target no longer touches are pruned with their findings.

Nothing is spent automatically: the freshness banner still only offers Re-run (the "no auto re-spend" rule). `ReviewProgress.reused` and `ReviewJobResult.reusedComponents` carry the count. The dock shows "N components unchanged, reused" while running and after completion, and the Re-run tooltip explains it.

#### 3. Suppression memory, per repo

Migration 8 also adds `finding_suppressions` (one JSON record each: file, summary, normalized summary, optional reason, source finding and target).

- **Made by:** the dock's "Not a problem" button (the eye-off icon) on an open, non-OK finding about a file. It opens an optional "why" field and sends `PATCH …/review/findings/[id] { resolved: true, dismiss: { reason? } }`. That adds an `answered` reply ("Not a problem: …"), which resolves the finding, and stores the suppression (one per finding; dismissing again replaces the reason). Applying a chat triage verdict of "wrong" does the same, with the chat's reason.
- **Matching:** at **read time** in the review GET (`matchSuppression`), so a dismissal applies at once to every stored review of the repo. A finding is suppressed when a suppression on the **same file** has a normalized summary with similarity ≥ `SUPPRESS_SIMILARITY` (0.8). The intent verdict and failed-call placeholders never match. `FindingDto.suppressed = { id, reason?, summary }`.
- **The dock:** suppressed findings are left out of the list, the verdict, the PR map areas, the copied markdown and the app map. A "Suppressed N" chip toggles them into the list, each with a "Suppressed: reason" chip and an **Un-suppress** button (`DELETE …/review/suppressions?id=`; `GET` lists them all).
- **The prompt:** each component's review call gets the suppressions on its changed files as `related.knownNonIssues`, rendered as "Known non-issues", with reasons, at most 15 (`lib/ai/prompts.ts`). The model is told not to raise them again unless the diff now makes them a real problem.
- **Reopening** a dismissed finding forgets its suppression.

#### Not done

- The MCP server's finding list and the jobs overview's defect count don't apply suppressions.
- There is no repo-level page listing every suppression; un-suppressing happens from a suppressed finding in the dock.
- Impact findings are grouped in the dock and can't be dismissed from there.
