### 6.15 Env variables: a variable catalog and what a change does to it (decided and built 2026-10-13)

The configuration surface of the app, one row per variable name: where the code reads it, where it is declared and where it is set — per environment, with the value — and what a PR does to all three. The Infra view (§6.12) already matches the env vars a workload sets against the vars the code it deploys reads. This view takes that further: it covers every source of a value, not only infrastructure, and it is useful in a repo with no IaC at all (most Next/Vite apps only have `.env*` files). Decided with the user up front (2026-10-13):
- **Where:** its own Graph view, **Env**, between Data and Files: **App map | API | Infra | Data | Env | Files | PR**. Like the other list views it's a full-column view (`LIST_VIEWS`, no review dock). It shows the last analysed commit, and with a diff selected it opens on that diff's change.
- **Sources that set a variable**, beyond what Infra already reads (Nomad `env`/`template`, k8s `env`/`envFrom`, Dockerfile `ENV`/`ARG`, `.env.example`): **all `.env*` files**, **CI workflows**, **Docker Compose** and **framework config**.
- **Values: shown, all of them.** It's a local tool on the user's own repos, and anything committed is already readable by everyone with the repo. The view shows every committed value, real `.env` files included. The model gets less (§5).
- **Findings:** four deterministic ones (§4): **a new read nothing declares**, **a secret exposed to the client**, **a committed secret value** and **a declaration removed but still read**. Everything else is shown, not counted.
- **Static only**, like Infra: nothing is run, no CI or host environment is read, no secret store is queried. Only **committed** files count. Analysis reads git objects (§6.10), so a git-ignored `.env.local` on the user's disk is invisible, and that's intended: the review is about the repo.

#### 1. Reading (cached by blob; `PARSE_VERSION` 9)
- **Code reads** extend `infra/code-facts.ts` (the lexical scan beside each parse). A read becomes `[name, line, flags]` (it was `[name, line]`), where the flags are:
  - **fallback**: `?? x`, `|| x`, `getenv("X", d)`, `environ.get("X", d)`, `${X:d}`, `os.LookupEnv` with an `if !ok` default on the next lines. When it's a literal, the fallback text is kept.
  - **required**: `!` non-null, `os.environ["X"]`, or a `throw`/`panic`/`sys.exit` guard on the same or the next line.
  - **client**: the file is client code. That means a `"use client"` file, anything a `"use client"` file imports (from the import graph), or Vite/CRA app code outside `server/`/`api/`/`*.server.*`. Names under `import.meta.env` are always client in Vite.
- **Declarations** are typed env schemas. They're read like code facts, with their own pattern set:
  - t3-env `createEnv({ server, client, runtimeEnv })`
  - a zod/valibot object parsed from `process.env` (`z.object({...}).parse(process.env)`)
  - envalid `cleanEnv`
  - pydantic `BaseSettings` fields (with `env_prefix` and `Field(alias=)`)
  - django-environ `env("X", default=)`
  - Go struct tags `env:"X"`, `envconfig:"X"` and `default:`
  - Spring `@ConfigurationProperties` (prefix + field, relaxed binding to `UPPER_SNAKE`)

  A declaration carries its type, its default and whether it's optional. A declared name also counts as read at the declaration's line.
- **`.env*` files** (new lexical reader `env/dotenv.ts`):
  - It reads `KEY=value`, `export KEY=`, quoted and multi-line values, `#` comments (the comment right above a key is kept as its description) and `${OTHER}` expansion. The expansion is kept as written and marked **interpolated**.
  - The **environment** comes from the file name: `.env` → `default`, `.env.production` → `production`, `.env.local` → `local`, `.env.production.local` → `production (local)`.
  - `.env.example`, `.env.sample`, `.env.template`, `.env.dist` and `.env.defaults` are **examples**. They *declare* names (documentation), they don't set them.
- **CI workflows:**
  - GitHub Actions `env:` at workflow, job and step level, with `${{ secrets.X }}` / `${{ vars.X }}` kept as a **secret ref** or **var ref**. The value lives in the host, so the name counts as "maybe set".
  - `.gitlab-ci.yml` `variables:` (global and per job), and `Jenkinsfile` `environment { }` with `credentials('id')` as a secret ref.
  - The CI's **environment** is the job name, or the GitHub `environment:` name when there is one.
  - Source tree change: the analysis skips dot-folders, so it doesn't see `.github` today. **`.github/workflows/*.y{a,}ml` is let through**, to be read only, not as a graph file. The Infra image→Dockerfile link (§6.12 As built) gets GitHub Actions `docker build`/`docker/build-push-action` steps from the same read.
- **Docker Compose** (`compose*.y{a,}ml`, `docker-compose*.y{a,}ml`), read for env only (Compose is still not an Infra tool):
  - `environment:` as a map or a list, and `env_file:`, which links to the `.env` file it names and so gives that file's values the service's scope.
  - `${X}` / `${X:-d}` / `${X?err}` interpolation is a **read from the host** at `compose up`, with its fallback or required flag.
  - Each service is an environment-like **target** named `compose:<service>`, and `build.context` links it to code the same way a Dockerfile does.
- **Framework config:**
  - `next.config.*` `env: {}`, which inlines values at build time and sets them for both server and client
  - Vite `define: { 'process.env.X': … }` and `envPrefix`, which changes the client prefix from `VITE_`
  - Spring `application*.properties|yml` `${X:default}`, already read for placeholders, now with the default; the profile suffix is the environment
  - Django `settings*.py`, whose reads are code reads already, with `settings/production.py`-style files as the environment
- **The client prefix per app** comes from its framework: `NEXT_PUBLIC_` (Next), `VITE_` or the `envPrefix` (Vite), `REACT_APP_` (CRA), `PUBLIC_` (SvelteKit/Astro), `EXPO_PUBLIC_` (Expo) and `NUXT_PUBLIC_` (Nuxt).

#### 2. The catalog (`lib/analysis/env/`)
`buildEnvCatalog` runs at the end of `analyzeTree`, after `buildInfraCatalog`, and takes the infra catalog's env sets as one more source rather than reading those files again (`AnalysisResult.env`).
- **One entry per name.** It holds:
  - `reads`: file, line, component, flags, fallback
  - `declarations`: schema, example file, with type, default, optional and description
  - `sets`: source kind, file, line, environment or target, value or secret ref, interpolated
  - `exposure`: server, client or both
  - `infra`: the Infra workloads that set it, as links into the Infra view
- **Scope.** Names are global, but a source only applies to the code it can reach:
  - a `.env*` file reaches code under its folder (the app root it sits in)
  - a Compose service, Nomad task or k8s workload reaches the components it deploys (Infra's deploy link, or Compose's `build.context`)
  - CI reaches the whole repo
  - `next.config` / Vite config reaches its app

  So in a monorepo, `apps/web/.env.production` doesn't cover a read in `apps/api`.
- **Status per name**, computed per scope and shown as tags:
  - **read, not set**: no source in scope sets it and the read has no fallback
  - **set, not read**
  - **undeclared**: read without fallback, and no schema or example in scope names it
  - **maybe set**: only secret or var refs, `envFrom` a Secret, or templated sources set it, so it's never reported missing
  - **secret-looking** (below)
  - **client**: exposed through the client prefix, `next.config` `env`, or a read in client code
  - **undefined in client**: a read in client code of a name without the client prefix. Next and Vite replace it with `undefined`. This is shown, not counted.
  - **platform**: `RUNTIME_ENV` from `infra/link.ts` moves to `env/platform.ts`, shared by both, and gains `PORT`, `GITHUB_*`, `RUNNER_*` and `CI_*`. Platform names are shown last and are never flagged.
- **Secret-looking** (`env/secret.ts`) is a short, deterministic classifier that's never a model call:
  - **Name**: `SECRET`, `TOKEN`, `PASSWORD`/`PASSWD`/`PWD`, `PRIVATE_KEY`, `API_KEY`, `*_KEY` (except `*_PUBLIC_KEY`/`PUBLISHABLE_KEY`), `CREDENTIAL`, `AUTH`, `SALT`, `COOKIE_SECRET`, `WEBHOOK_SECRET`.
  - **Value shape**: a connection URL with a password in its userinfo (`postgres://u:p@…`), a PEM block, a known token prefix (`sk-`, `sk_live_`, `ghp_`/`gho_`/`github_pat_`, `glpat-`, `xox[bp]-`, `AKIA`/`ASIA`, `AIza`, `-----BEGIN`), or a ≥ 24-char base64/hex string with high entropy.
  - **Placeholder** (never a secret value): empty, `changeme`, `change-me`, `xxx…`, `***`, `<…>`, `your-…`/`your_…`, `example`, `secret`, `password`, `test`, `dummy`, `todo`, `${…}`, or a localhost URL without a password.
- **Ids** are stable across commits: the variable's name, and a set's id is `source:file:target:name`.

#### 3. Storage and the change
- The default branch's catalog goes in an `env_catalogs` table, laid out like `infra_catalogs` (SQLite migration 6, `ANALYSIS_VERSION` 9). The comparison is stored as `env` in the `target_graphs` row's data, beside `api`, `infra` and `schema`.
- `compareEnv(base, head, changed)` (`env/compare.ts`) gives one entry per name with:
  - **reads added / removed** (file:line)
  - **declarations added / removed / changed** (type, default, optional)
  - **sets added / removed / value changed**, per environment or target, shown as a before → after cell (+ green, − red, ~ amber)
  - **status changes**: newly read-not-set, newly client, newly undeclared
- A name is **new** when the base doesn't read, declare or set it anywhere, and **gone** when the head doesn't.

#### 4. Findings (`category: "env"`, ids from the rule and the name)
Each is deterministic, without a model call, and synced by the target-graph job beside `structure` and `infra` (`STATIC_FINDING_CATEGORIES` gains `env`; the review dock's static chips gain **Env**):
- **A new read nothing declares** (`concern`). The diff adds a read of a name with no fallback, and the head has no declaration (schema or example) and no set for it in that read's scope. Maybe-set names and platform names never fire. One finding per name, anchored at the first added read.
- **A secret exposed to the client** (`defect`). In the head, a secret-looking *name* is exposed to the client: through the client prefix (`NEXT_PUBLIC_STRIPE_SECRET_KEY`), through `next.config` `env`, or through Vite `define`. It fires only when the diff introduced the exposure (the name, the prefix or the config entry). It's anchored at the declaration, set or config line the diff added.
- **A committed secret value** (`defect`). The diff adds or changes a value that is secret-looking by name or by shape, and isn't a placeholder, in any committed file this view reads: `.env*` (examples included), Compose, CI, `next.config`, Spring config, Dockerfile `ENV`/`ARG`, k8s/Nomad env literals. A code read's literal fallback counts too (`process.env.X ?? "sk_live_…"`). The finding text names the variable and file:line and **doesn't quote the value**. The view shows it anyway (decided above).
- **A declaration removed, still read** (`concern`). The diff removes the last declaration or the last set in scope of a name the head still reads without a fallback. That's an `.env.example` key, a schema field, or a Compose/CI/infra set. This generalises Infra's "env var no longer set": when Infra's finding covers the same workload and name it wins, and this one doesn't fire (no duplicates).
- The review prompt of each affected component lists these as **already reported** and is told not to repeat them (§6.12's convention).

#### 5. Where it shows
- **Env view** (`EnvView`). The toolbar has the view switch, then with a diff selected **Env changes N | All variables M**, then the filters: scope (app or package), environment, status tags (read-not-set, set-not-read, undeclared, secret, client, platform), and a search over names and values.
  - **All variables** is a **matrix**. Rows are names, grouped by **prefix** (`DATABASE_*`, `NEXT_PUBLIC_*`, `STRIPE_*`; a group needs ≥ 2 names) or by **component** (the readers' owners), switchable. The columns are:
    - **Read by**: component chips, with a count, ✱ for required and `?? x` for a fallback
    - **Declared**: schema/example, type, default
    - **one column per environment/target** that sets anything (example, default, production, `compose:api`, `nomad:api/web`, CI `deploy`): the value, a 🔒 ref chip for secret refs, `—` when not set, `↳` when it's inherited from a base `.env`
    - **tags**

    Environments with no set for any visible row are hidden. Values are shown in full, monospace and truncated with a tooltip. Secret-looking values are shown too, with a small "secret" tag. A per-browser **Hide values** toggle blurs them for screen-sharing; it's off by default.
  - **A row opens in place**:
    - every read (file:line, opens the file viewer), with flags
    - every declaration, with its description comment
    - every set, with its value, file:line and how it's inherited
    - the Infra workloads, which open the Infra view at that resource
    - the client/server exposure and why
  - **Env changes** is a flat list, findings first, then gone → new → changed, with the changed rows open (up to 8) and their changed cells marked +/−/~.
- **Left column:** an "Env" section with `+new −gone ~changed` and the changes, **only when the diff changed env** (as for API, Infra and Schema). Each line opens the view at that name.
- **App map explainer:** "Reads env vars": the names the card's files read, with tags. Infra's "Reads env vars nothing sets" becomes a filter link into this view (one source of truth for that list).
- **Review:**
  - Each component's prompt gets "Configuration this change touches", which holds:
    - the names its changed files read, declare or set
    - for each, its declaration, fallback, which environments set it, and its exposure
    - the env change entries for those names
  - **Values in the prompt** go through a narrower rule than the view. A value is included only when it's non-secret-looking by name and shape. A secret-looking one is rendered as `<set, 41 chars>` / `<placeholder>`. The model's endpoint is a third party the user configured, and a review never needs a secret's text to judge the code.
  - Env-only files (a `.env.example`, a workflow) aren't graph files. A PR touching only those is still reviewed: the env change goes to the components that read the changed names (or, when nothing reads them, to the intent check alone).
- **Chat and MCP:** `list_env` (filter by name, status, environment, scope) and `get_env_changes` (PR chat). The same values rule as the prompt applies, since both go to the model.
- **Routes:** `GET /api/repos/[repoId]/env-catalog`.

#### Limits
- **Dynamic names** aren't read: `process.env[name]`, `getenv(f"{p}_URL")`, and config loaders that read a whole prefix (`dotenv-flow` cascades are modelled; `convict`, `config`/`node-config` and `rc` aren't). Neither are names built in CI scripts (`echo "X=1" >> $GITHUB_ENV`) or a `.env` written at deploy time.
- **Host values are unknown:** CI secret and var stores, Vault, Consul, k8s Secrets, Vercel/Netlify/Fly project env. A name set only there shows as **maybe set**, never as missing. So a repo that keeps everything in its host's dashboard gets mostly "maybe set" or "read, not set". Without an example or a schema the view can't tell those apart. That's what the "undeclared" tag is for.
- **Client detection** follows imports from `"use client"` files and the framework's conventions. Code reached only through dynamic imports, or a custom bundler setup, may be misclassified, which is why "undefined in client" is shown, not counted.
- **Only committed files** are seen (above). Because the analysis reads git objects, a `.env` file that's git-ignored on disk never reaches it, so it can't be counted twice.

Covered by `npx tsx lib/analysis/env/smoke-test-env.ts`:
- fixtures: a Next app (t3-env schema, `.env.example`, `.env.production`, a `"use client"` read of a server name, a `NEXT_PUBLIC_*_SECRET`); a Vite app with `envPrefix`; a FastAPI service with pydantic `BaseSettings`; a Go service with `envconfig` tags; Compose with `env_file` and `${X:-d}`; a GitHub workflow with `secrets.*` and `environment:`; a monorepo where scopes keep `apps/web`'s `.env` from covering `apps/api`
- the comparison, with each of the four findings, and Infra's "no longer set" winning over the duplicate

Regression-check the user's own repos (GraphReview, MultiTool), plus a cloned public Next.js SaaS starter and microservices-demo for the Infra overlap.

#### As built (2026-10-13)
Built as specified above. Where the build differs, or the spec was silent:
- **Reading.**
  - Env source files are read by `lib/analysis/env/read.ts` in-process and cached by blob, under their own key (`PARSE_VERSION:env-<reader>:…`). A file can be an env source as well as code or infra (`next.config.js`, `.gitlab-ci.yml`). For `.env*` files, workflows and framework configs the key includes the path, because the target name comes from it.
  - `.envrc` and `*.env` (Compose `env_file`s such as `prod.env`) count as `.env` files.
  - Code reads still come from the lexical scan in `infra/code-facts.ts`. A read is now `[name, line, flags?]`, where the flags are `f` (fallback: the literal, or `…`), `r` (required) and `m` (`import.meta.env`). `CodeFacts` also gained `client` (`"use client"`), `server` and `decl`.
  - `server` marks a `"use server"` file or one that imports `server-only`. Client-ness stops at such a file, because a client component that imports server actions gets RPC stubs, not their code.
  - Writes aren't reads: `process.env.X = …`, `os.environ["X"] = …` and `delete process.env.X` are skipped, and `??=` / `||=` count as a fallback. This is shared with the Infra links.
  - Reads in test and fixture files (`*.test.*`, `*.spec.*`, `__tests__/`, `fixtures/`, `smoke-test*`, `_test.go`, `test_*.py`, …) are kept but marked `test`, and never raise a gap or "undefined in client". A lexical scan can't tell a fixture string from code.
  - A JS read that handles a missing value counts as having a fallback (`…` when it isn't a literal). That covers `X?.trim() || "d"`, `Number(X) || 1`, `X !== "1"`, `X ? a : b`, `X && …` and a bare `if (X)`, but not one with a throw/exit guard.
  - All four rules came from running the catalog on GraphReview itself. Before them it had 30 undeclared names (assignments, fixture strings) and 3 false "undefined in client" tags, which came through a `"use server"` actions file.
- **Schemas.** `env/declare.ts` reads the following:
  - t3-env (`server:`/`client:` sections; `runtimeEnv` is skipped)
  - zod/valibot objects in files that touch `process.env`/`import.meta.env`
  - envalid
  - pydantic `BaseSettings` (`env_prefix`, `alias`)
  - django-environ
  - Go `env:`/`envconfig:` tags

  **Spring `@ConfigurationProperties` isn't read**. Spring placeholders still are, now with their `${X:default}` as the fallback.
- **The one dot-folder.** The walk now lets `.github/workflows/*.yml|yaml` through (`walk.ts` `WORKFLOW_FILE`), and nothing else under `.github`. Infra reads those files as CI scripts too, so `run: docker build -t …` steps now feed its image links. `docker/build-push-action` steps aren't parsed.
- **Tags.**
  - The spec's "read, not set" became two tags. **undeclared**: nothing in scope declares or sets the name. **not-set**: a schema or example declares it, but no committed source gives it a value. Most apps keep real values in a git-ignored `.env.local`, so a declared-only name is normal and shown grey.
  - Each read carries its own `gap`, which the findings use.
  - A declaration covers reads in the nearest scope root (a framework config or `.env*` folder); an example covers its own folder. A CI set covers the whole repo. An infra workload covers the folders its deploy link resolves to, or the whole repo when that link isn't resolved.
  - `infra/link.ts` now takes its platform names from `env/platform.ts`, which also covers `PORT`, `GITHUB_*`, `RUNNER_*`, `CI_*` and Vite's `MODE`/`DEV`/`PROD`/`SSR`/`BASE_URL`.
- **Secret classifier.** A connection URL to localhost, or with a stock password (`user:pass@`), counts as a placeholder.
- **Findings.**
  - **committed-secret**: in an example file, only a value shaped like a secret counts. A secret name alone isn't enough, since examples often hold realistic-looking dummies.
  - **secret-to-client**: judged by name only. **declaration-removed**: needs the read's gap to have been closed at the base.
  - `InfraFinding` gained `name` (for `env-unset`), so the env comparison can skip its duplicate.
  - The rule key is `env:<rule>:<name>` (plus file:line for committed secrets), so replies survive re-comparisons.
- **The view (`EnvView.tsx`, `env-view-model.ts`, `EnvChangesSection.tsx`, `useEnvCatalog.ts`).**
  - The environment columns **scroll sideways** under a sticky name column, and an opened row's detail stays pinned to the visible width.
  - The "Read by" chips are one per **component** reading the name (the owning component of each reading file, looked up when the catalog is served, so a re-clustering shows without a re-analysis), labelled with the folder its reading files share (`analysis/syntax · lib/analysis/syntax`); clicking one shows the component on the map. Reads in no known component fall back to their folder, two levels deep. The "Folder" grouping still uses the two-level folder.
  - Chat's `show` takes `{"kind":"env","name":"DATABASE_URL"}` and opens the Env view at that row (DESIGN.md §6.7).
  - The scope filter lists framework-config and `.env*` folders.
  - Tag chips in the toolbar filter the rows, and several selected together must all match.
  - "Hide values" blurs every value and is remembered per browser.
  - `↳ default` marks a `.env.<env>` cell that the folder's `.env` fills.
  - With a diff selected, "Env changes" opens with up to 8 entries expanded. Each shows its findings' summaries and a `where | − before | + after` grid.
- **Review.** `ReviewRelatedContext.env` is rendered as "Configuration this change touches". It holds the head catalog's lines for the names the component's changed files read, declare or set, then `change:` lines. Env findings go into "already reported", and the intent check gets `describeEnvChange`. All values pass through `valueForModel`.
  - **Built 2026-10-14:** env sources that aren't code or infra (`.env*` files as `dotenv`, CI workflows as `ci`, Compose as `compose`) are graph files, clustered into their folder's component, so a PR that only touches them gets a component review with its env names as context. One only the head has (a new `.env.example`) joins the component owning its nearest analysed folder, like a new migration. `PUBLIC_` counts as a client prefix only when the repo has a SvelteKit or Astro app (or a config names it), since it's a plain word elsewhere — MultiTool's server-side `PUBLIC_BLOB_READ_WRITE_TOKEN` was flagged as client.
- **Chat and MCP:** `list_env` (query, tag, environment) and `get_env_changes`; the server instructions describe the `env` category. A chat `show` action for a variable isn't built.
- **Storage:** `env_catalogs` (SQLite migration 6), `ANALYSIS_VERSION` 11, `PARSE_VERSION` 11 (9 was the first build; 10 adds writes, `"use server"` and test files; 11 adds reads that handle a missing value).
- **Verified:** with `smoke-test-env.ts`, then end to end on a two-branch copy of its fixture in an isolated `npm run dev` (its own `GRAPHREVIEW_HOME` and `GRAPHREVIEW_DIST_DIR`): the matrix, sideways scroll with the pinned name column and detail, the left-column Env section, the four findings in the review dock under the Env chip, and no server errors.
  - The smoke test also has a Vite app with `envPrefix`.
