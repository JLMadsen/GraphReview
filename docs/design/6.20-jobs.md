### 6.20 Jobs: seeing what runs in the background (decided and built 2026-10-16)

Background work is visible today only as hover-to-see-logs on the status that started it: the repo's Analyzing badge (`app/status-log-hover.tsx`), the review dock and the preview tab (each `?logs=1` on its own route). That shows one job at a time, says nothing about work queued behind it, and disappears once the job finishes. So you wait without knowing why, and a failure is easy to miss once the status text changes. This section makes all jobs visible: a **header indicator with a Jobs drawer** across repos, plus **inline status and failures** in the views that start the jobs.

Decided with the user (2026-10-16), after a round of questions:
- **No log of user actions.** GraphReview is one person's local tool (§2, decision 6). Who did what is already stored as state: finding responses, checklist answers, chat, git. The useful part of such a log, "why is this running?", is the job's **trigger** (§3).
- **Both places:** inline status where the work shows up, and a global drawer for everything else.
- **No new history.** Each queue's existing retention stays (below). "Recent" is whatever is still in the `jobs` table. Revisit only when there's a concrete question that history would answer.
- **For users and the developer alike:** jobs are listed under plain names. Logs are one click away, behind the row.

#### 1. What a job is here
The six queues in `lib/jobs/*queue*.ts`, all rows of the `jobs` table (§12), with their lines in `job_logs`:

| Queue | Shown as | Target | Cancel | Kept after it ends |
|---|---|---|---|---|
| `analysis` | Analysis | default branch @ sha | — | done 24 h / 50, failed 7 d / 50 |
| `target-graph` | Compare | PR or refs | — | 24 h / 200 |
| `review` | Review | PR or refs | yes (`review-queue.ts` cancellation) | done 24 h / 50, failed 7 d / 50 |
| `app-map` | App map | level (+ card) | yes (`cancelAppMap`) | done 24 h / 50, failed 7 d / 50 |
| `preview-scan` | Preview scan | PR or refs | — | as `preview` |
| `preview` | Preview | file in PR or refs | — | 24 h / 200 |

The repo tree, stats and catalog reads aren't queued jobs (they run inside a request or a cache), so they don't appear. All jobs that exist are shown, with no "routine" toggle. Sorting keeps the important ones on top (§2).

A job's id is deterministic per repo and target (`analysisJobId`, `previewJobId`, …), so re-running a target replaces its row. The drawer shows one row per target, not one per attempt.

#### 2. The drawer (`components/jobs/JobsDrawer.tsx`)
- **Header indicator** (app header, every page):
  - A spinner with "N running · M queued" while any job runs or waits.
  - A red "K failed" for failed jobs the user hasn't opened yet.
  - A plain "Jobs" when idle with no unseen failures (as built; first decided as nothing at all).
  - Click toggles the drawer. The palette (§6.18) gets a **Jobs** command that opens it.
- **Drawer:** a panel under the header with two lists.
  - **Now:** running, then queued.
  - **Recent:** failed, then finished, then cancelled, each newest first.
  - Filter chips: **All · Active · Failed · This repo** (This repo only inside a repo).
- **A row:** state icon, kind, repo · target, then a second line:
  - **Running:** progress (each queue's `progress`: review components done of total, app-map cards, analysis phase) and elapsed time.
  - **Queued:** its position in that queue ("2nd in the review queue"), since queues run in FIFO order at their worker's concurrency (`worker/index.ts`). No cross-queue "waits on X". Jobs don't record dependencies, and inventing them would lie.
  - **Failed:** `failed_reason` in danger text, and the duration.
  - **Done:** the result in one phrase (review: "9 findings · 2 defects"; analysis: "412 files"), the duration, and how long ago.
  - The row links to where the result lives (the review's Graph tab, the preview tab, the app map).
- **Expanding a row** shows "Triggered by: …" (§3), then the job's `job_logs` lines. The newest 200 are read on demand, as the hovers do now.
- **Actions:**
  - **Cancel** on running and queued review and app-map jobs, through their existing cancellation.
  - **Run again** on failed jobs, re-enqueuing with the same data through the queue's existing `enqueue*`.
  - A failure caused by configuration (no AI provider, provider timeout, no Docker) links to the setting instead of offering Run again. Retrying wouldn't help.
- **Unseen failures:** opening a failed row (in the drawer, or its inline failure, §4) marks it seen, stored in `kv` per job id + `finished_on`. That's what clears the red count. A job that fails again counts again.

#### 3. Triggers, inferred
"Triggered by" is inferred from the queue and the job data, not passed in by every enqueue call. That way a new job kind needs no extra plumbing:
- **review:** `only: "failed"` → "Re-review failed components", otherwise "Review".
- **app-map:** `mode` / `card` → "Explain card X", "Re-place map", ….
- **preview:** `inputs` / `mocks` set → "Preview with edited inputs", otherwise "Preview".
- **analysis:** the first run for a repo → "Repo added", otherwise "New commit on default branch" or "Refresh". The difference comes from the previous analysed sha.

Where the data can't tell, the line is left out. It never guesses.

#### 4. Inline status and failures
Each view that starts a job shows that job's state where the user is already looking, so the drawer isn't the only way to find out:
- **Repo status badge** (Analyzing/Refreshing): keeps its log hover and adds "queued, 2nd" while waiting. A failed analysis shows inline with its reason and Run again.
- **Review dock:** "Queued, 2nd in the review queue" or "Comparing refs first" (while that target's `target-graph` job runs). A failed review shows in the dock with its reason, the logs and Run again. A cancelled one says so plainly and isn't styled as an error.
- **Preview tab** and **app map:** the same pattern (queued position, failure with reason, logs, Run again).

Showing a failure inline marks it seen (§2). The red count is for failures in views you aren't looking at.

#### 5. API
- `GET /api/jobs?repo=&state=` → rows from `jobs` (no `data` blobs beyond the fields §2–3 need), with queue position computed for waiting rows. The indicator polls it every ~2 s while anything runs and ~15 s when idle. The drawer polls it while open.
- `GET /api/jobs/[queue]/[id]/logs` → the newest 200 `job_logs` lines.
- `POST /api/jobs/[queue]/[id]/cancel` and `/retry` → delegate to the queue's own cancel and enqueue functions. Return 409 where the queue has none.
- `POST /api/jobs/seen` → marks failures seen.

The existing per-view `?logs=1` routes stay. The inline views keep using them.

#### 6. Not in scope
History beyond current retention. Duration trends. Notifications or toasts. Showing in-request work (tree, stats, catalogs). Dependencies between queues. A log of user actions.

#### As built (2026-10-16)
- **Code:** `lib/jobs/jobs-overview.ts` (rows, positions, triggers, results, cancel/retry delegation, seen marks), routes under `app/api/jobs/`, `components/jobs/` (`store.ts` — one shared poll for the indicator, drawer and inline states; `JobsDrawer.tsx` — indicator + drawer; `JobParts.tsx` — logs, actions, inline queued/failed). Inline: `app/analysis-job-inline.tsx` (badge "· queued, 2nd", failed card on the Repos page), `ReviewPanel`, `PreviewPanel`, `AppMapView`. Smoke test: `lib/jobs/smoke-test-jobs-overview.ts`.
- **One poll for everything.** The inline views read queue position and failure from the same `/api/jobs` poll as the header (~2 s active, ~15 s idle), so no job ids are threaded to the client; rows carry `repoId`, `targetKey` and `filePath` to match on. The views' own `?logs=1` hovers are unchanged.
- **Run again inline** goes through the view's own re-run (review dock `Re-run`, preview `Run`, app map `generate`) so its own polling picks the new job up; the drawer uses `POST …/retry`. The review dock shows a Settings link instead of Run again while no AI provider is configured.
- **Triggers:** app-map `split` reads "Split card X" (there's no "explain one card" mode); target-graph and preview-scan read "Opened the change" (both start when a target is read). Analysis "New commit on default branch" vs "Refresh" compares the sha the running job logs (`analyzing … at <sha>`) with the repo's previous analysed sha, so it shows only once the run has resolved its source; a queued re-analysis after an `ANALYSIS_VERSION` bump reads "GraphReview update (re-analysis)". Finished analyses have no trigger line (their sha is now the repo's).
- **Config failures** are recognised from `failed_reason` text (AI provider not configured, Docker not running/installed, provider timeout) and link to `/settings`.
- **Cancelled** = a failed row whose reason is the queue's "Cancelled by user." — listed under Recent, never counted as a failure.
- **Seen marks** live in `kv` as `job-seen:<queue>:<id>` = `finished_on`, kept 8 days (past the longest failed retention).
- **Indicator always shown** (changed 2026-10-16, after building): a plain "Jobs" when idle with no unseen failures, instead of nothing, so Recent is one click away without the palette.
- **Not done:** the repo header's quiet status text ("Analysis failed") has no inline Run again — the Repos page card and the drawer have it.
