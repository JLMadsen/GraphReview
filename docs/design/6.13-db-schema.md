### 6.13 Database schema: a schema catalog, its diff and the review context (decided 2026-10-10, built 2026-10-10)

The API catalog's counterpart for the database: which tables a repo's migrations, schema files and ORM models declare, which code uses them, and what a PR does to them. Spec'd in a separate session on 2026-10-08, decided with the user on 2026-10-10:
- **Where:** its own Graph view, **App map | API | Infra | Data | PR**: an ER canvas, with a **Canvas | List** switch.
- **Findings:** destructive operations and four migration hazards are counted (§5 below). **Model ↔ migration drift is not a finding**: it goes into the review prompt as context, and the model decides whether it matters.
- **Review context:** each component's review gets the tables its code touches, with the PR's changes marked, so the model can flag a **new column used wrongly** (an insert that never sets a new NOT NULL column, a read of a dropped column, a new enum value a `switch` doesn't handle). These are ordinary `change` findings from the model.
- **Endpoint ↔ table links in v1, through models, query builders and raw SQL** (re-decided 2026-10-10). A link found in SQL text says so.
- **Static only:** no live database, no connection string.
- **Built after the infra catalog** (§6.12): `PARSE_VERSION` 5, `ANALYSIS_VERSION` 5, SQLite migration 5.

#### 1. Where the schema comes from
Each table and column is labelled with the best source that defines it:

| Rank | Source | v1 | Confidence |
|---|---|---|---|
| 1 | **Migrations**, replayed in order | Prisma `migrations/*/migration.sql`, Drizzle `drizzle/*.sql` (+ `meta/_journal.json`), TypeORM migration classes (`queryRunner.query(...)` SQL and `createTable`/`addColumn` calls), Django `migrations/*.py` operations, Alembic `op.*` calls, plain SQL folders (golang-migrate `*.up.sql`, dbmate, Supabase `supabase/migrations`, Flyway-named `V<n>__*.sql`) | Exact |
| 1 | **Migrations in code** (added 2026-10-10) | DDL in the app's own string / template literals: the elements of one array / list literal are migrations in element order (a `MIGRATIONS` array run with `db.exec(MIGRATIONS[version])`, a Go `[]string{…}`); other DDL literals of a file are a schema-file-like source in line order | Exact (a statement with a `${…}` hole is opaque) |
| 2 | **Declarative schema files** | `schema.prisma`, Drizzle `pgTable`/`mysqlTable`/`sqliteTable`, `schema.sql` / `structure.sql` | Exact |
| 1–2 | **`.sql` by content** (decided 2026-10-11) | Outside migration folders, any non-test `.sql` that is mostly CREATE TABLE is a schema file, whatever its name; a file beside it that is mostly ALTER / DROP / CREATE INDEX / RENAME is its change log (line order, each comment-led block one entry). A trial replay of the changes onto the creates picks the convention: all apply cleanly → creates + changes; all already in the creates → the creates, changes as history; mixed → the creates as written and an order problem naming the clashes | Exact |
| 3 | **ORM models** | TypeORM `@Entity`/`@Column`/relations, Django `models.Model`, SQLAlchemy `Column`/`Mapped[]`/`relationship`, SQLModel | Inferred; table names follow each framework's rules (Django `app_model`, `__tablename__`, TypeORM naming) |

- **v2:** Rails, Sequelize, Knex, Mongoose (collections, no FKs), Kotlin Exposed, JPA with Flyway/Liquibase. **Out:** EF Core (no C#), Go ORMs (Go parsing is still regex).
- When migrations and models both exist they're merged; a model field with no column, or a migrated column no model maps, is **drift**. Drift shows in the explainer and goes to the review prompt; it is never counted.
- **Migration order:** Prisma and Drizzle by folder/journal order, plain SQL and Flyway by version or filename, Django by the `dependencies` graph, Alembic by the `down_revision` chain, TypeORM by the class timestamp. When the order can't be worked out (two Alembic heads, a Django cycle) the problem is shown, not guessed.
- **Databases:** one per migrations folder / datasource (`DbSchema.databases`), so a monorepo with several is fine. Dialect from `schema.prisma`'s provider, Drizzle's table builder, Django/SQLAlchemy settings where literal, else guessed from the SQL and shown as guessed.

#### 2. Parsing (parse worker, cached by blob; `PARSE_VERSION` 5)
- **Models:** `routes.mjs` already extracts `models` (class fields) and decorated classes. Extend those facts with column, relation and table-name annotations (TypeORM decorators, Django field calls with `null`/`default`/`ForeignKey`/`db_table`, SQLAlchemy `Column(...)`/`mapped_column(...)`/`__tablename__`).
- **Migration code:** Django operations (`CreateModel`, `AddField`, `AlterField`, `RemoveField`, `RenameField`, `RenameModel`, `DeleteModel`, `AddIndex`, `RunSQL`), Alembic `op.create_table`/`add_column`/`alter_column`/`drop_*`/`rename_table`/`create_index`/`execute`, TypeORM `queryRunner` calls. Anything else (`RunPython`, data loops) is an **opaque step** in the history.
- **Non-code files** (`.sql`, `.prisma`, Drizzle journal): a new `lib/analysis/syntax/schema.mjs` reader.
- **SQL DDL:** a tolerant, self-contained parser (air-gapped, no dependency) for CREATE / ALTER / DROP of TABLE, INDEX, TYPE/ENUM and VIEW, plus RENAME, across Postgres, MySQL and SQLite. Anything it doesn't recognise (DO blocks, data updates, dialect extras) is kept as an **opaque statement** so the history doesn't lose it.

#### 3. The catalog (`lib/analysis/db/`)
`buildDbSchema` runs at the end of `analyzeTree`, beside the API and infra catalogs (`AnalysisResult.db`). Resolvers per source; one that throws costs only its own database.
```
DbSchema { databases: Database[] }
Database { id, dialect?, dialectGuessed?, sources[], tables[], enums[], views[], opaque[], orderProblems[] }
Table    { id: "<db>:<schema>.<name>", columns[], pk, indexes[], fks[], checks[],
           source: "migration"|"schema"|"model", definedAt {file,line},
           history: MigrationRef[], models: declId[], component?, drift[] }
Column   { name, type, nullable, default?, unique?, generated?, source, modelField? }
Fk       { columns, refTable, refColumns, onDelete?, inferred?: true }   // inferred = from ORM relations only
```
Table ids are stable across commits, like endpoint ids. `component` is the component holding the table's model, else its migration.

#### 4. Links to code
- **Table → model → code:** the model class by declaration, then the symbol graph's references to it (§6.10).
- **Table uses in code** (new facts in the parse, per function), each with how it was found and read / write where the call says so:
  - **model:** a reference to the table's model class or its accessor (Django `Order.objects`, SQLAlchemy `select(Order)` / `session.query(Order)`, TypeORM `getRepository(Order)` / `@InjectRepository(Order)`, Prisma `prisma.order.*` delegates, a Drizzle table object such as `db.select().from(orders)`).
  - **query builder:** a table named as a string in a builder call: Knex `knex('orders')` / `.table()` / `.from()` / `.join()`, Kysely `selectFrom` / `insertInto` / `updateTable` / `deleteFrom`, TypeORM `createQueryBuilder().from('orders')`, SQLAlchemy `table('orders')`.
  - **raw SQL:** string and template literals passed to a SQL call (`$queryRaw` / `$executeRaw`, ``sql`…` `` tags, `text()`, `cursor.execute`, `queryRunner.query`, `db.query` / `pool.query`, `RunSQL`) and, outside those calls, literals that start like SQL (`SELECT`, `INSERT`, `UPDATE`, `DELETE`, `WITH`). Table names after `FROM` / `JOIN` / `INTO` / `UPDATE` / `DELETE FROM` are kept **only when they match a known table**. These links are marked **from SQL text**.
- **Endpoint → table:** the API catalog's reach (§6.11) already marks data access; an endpoint is linked to every table that a function it reaches uses, in any of the three ways. The API explainer gets "touches: orders, order_items"; the table panel gets "read/written by: `POST /orders`, …", with SQL-text links marked.
- **Component → tables:** the tables its files use, in any of the three ways. This drives the review context (§6).

#### 5. The change and findings
- The target-graph job adds `db: compareSchemas(base, head)` (`db/compare.ts`) to the `target_graphs` data, base being the merge-base.
  - Tables added, removed, renamed (an explicit RENAME, or a removed and an added table with matching columns).
  - Columns added, dropped, retyped, nullability or default changed. Indexes, FKs, checks and enums added, removed or changed.
  - The migrations the PR adds, and drift the PR introduces ("model changed, no migration" and the reverse).
- **Findings** (`category: "schema"`, ids derived from the table/column and the migration, `concern`, no model call), only from migrations the PR adds:
  - **Destructive:** DROP TABLE or DROP COLUMN (data loss).
  - **NOT NULL without a default** added to an existing table.
  - **Type narrowing** (`text → varchar(50)`, `bigint → int`, a smaller precision).
  - **Column or table rename**, which breaks the old code during a rolling deploy.
  - **Postgres index locks:** `CREATE INDEX` without `CONCURRENTLY` on an existing table, and an FK whose columns have no index.
  - Not counted: a missing down migration (Prisma and Django have none).
- As for infra, the review prompt lists these as **already reported**.

#### 6. Review context
Each component's review prompt gets "Tables this code touches": the full definition of each table its models map to, with this PR's changes marked (+ / − / ~), the drift on those tables, and the already-reported schema findings. It is fitted to the token budget (§9.1) after the diff: changed tables first, then unchanged ones, columns trimmed last. The prompt asks the model to check that inserts and updates set new NOT NULL columns, that dropped or renamed columns aren't still read, and that new enum values are handled. A component that changes only migrations or models also gets it. The intent check gets the whole schema change; the PR chat gets the change plus `list_tables`.

#### 7. Where it shows
- **Data view** (`DataView`): the toolbar has the view switch, then with a diff selected **Changed only N | All tables M**, then **Canvas | List**, the database picker and search.
  - **Canvas:** an ER diagram. Each card lists its columns (key marker, name, type, `?` when nullable, + / − / ~ on a diff, dropped columns struck); past 14 columns, keys and changed ones are kept and the rest is "+N more". FK edges run **column to column** (CardFlow `ports`), dashed when inferred, labelled `cols → refCols` when lit. "All tables" boxes cards by **owning component**, falling back to Postgres schema, but only when that gives two or more boxes. **Revised 2026-10-11** after the user compared it to the mockup: the first build drew compact cards (name and changed columns only) and also boxed by name prefix, which put ELK in hierarchical mode, so unconnected tables stacked in one tall column and the edges bundled into one faint lane. Prefix groups now only apply in the list. "Changed only" shows changed tables plus their direct FK neighbours, faded. Changed cards: amber edge, new ones green, removed ones red and struck.
  - **List:** like the API view, rows opening in place.
  - **Explainer** (right column on the canvas, in place in the list): source badge and file, findings, columns with source badges (+ − ~ on a diff), indexes, FKs in and out, the **migration timeline** for the table, the mapped models, the endpoints that read or write it, and drift.
- **Left column:** a "Schema" section, `+1 table ~2 · 3 migrations · ! 1 destructive`, only when the diff changed the schema.
- **PR map:** area cards get a `⛁N` badge for the tables they touch.
- **MCP:** `list_tables` and `get_schema_changes`.
- **Routes:** `GET /api/repos/[repoId]/db-schema`.

#### 7b. A pinned source file (decided 2026-10-11)
- When the analysis finds nothing — or finds the wrong thing — the user picks **one file** in the Data tab as the repo's schema source. The empty state lists ranked candidates (files of the analysed commit holding schema statements: `.sql`, `.prisma`, code with DDL literals; non-test first, then by CREATE TABLE count, each with its table count and a "Use this file" button) and a search over every file of that commit to pick any other.
- **Pinned replaces auto-detection**: the repo's only database is built from that file, for the default branch's catalog and for every PR and ref comparison (read at base and at head; missing at a commit → an order problem, never an empty schema). `.sql` is replayed in line order, a statement that doesn't fit the schema so far kept opaque and listed; `.prisma` as a Prisma schema; a code file's DDL literals as "SQL in code" reads them. Uses, endpoint links, review context and findings work as for any database.
- The Data view's source line says "Source: <file> (pinned) · Change · Use auto-detect"; with an auto-detected schema it offers "Choose the source file…". Changing or clearing the pin re-runs the analysis and drops the stored comparisons so every target recomputes. `list_tables` (chat and MCP) says when the source is pinned.
- **Routes:** `GET /api/repos/[repoId]/db-schema/candidates`, `PUT` / `DELETE /api/repos/[repoId]/db-schema/source`.

#### 8. Storage
`db_schemas` table (one row per repo, `repo_id`/`sha`/`computed_at`/`data` like `api_catalogs`; SQLite migration 5; `ANALYSIS_VERSION` 5).

#### Limits
- No live database: drift between the migrations and the real database is invisible.
- Schemas built at runtime in code aren't read. SQL assembled at runtime (table names in variables, string concatenation across calls) isn't linked, and SQL-text links can be wrong (a table name in a comment or an unrelated string), so they're marked.
- `RunPython` / data migrations are opaque.
- NoSQL schemas are only as good as their ODM definitions (v2).

Covered by `npx tsx lib/analysis/db/smoke-test-db.ts`: the SQL reader (Postgres identity / arrays / checks, `DO` blocks, multi-action `ALTER TABLE`, `CREATE INDEX CONCURRENTLY … WHERE`, a MySQL table, query table names with CTEs left out, type narrowing); one fixture per v1 source (a Prisma schema and migrations, Drizzle tables and journal, TypeORM entities and a migration class, a Django app with migrations, SQLAlchemy models with an Alembic chain, a golang-migrate folder, and DDL in code: a `MIGRATIONS` array of template literals with a query file and a smoke test's throwaway DDL, and a Go slice) in one tree; merging and drift; the endpoint links (model — Prisma delegate, Drizzle object, Django class —, query builder — Kysely, SQLAlchemy `table()` —, SQL text — a tagged template, Python `text()`, a Go literal —, and a literal naming an unknown table, which is dropped); a head whose migrations produce every finding (one from an appended array element), with an edited element shown as edited; and the review context, rendered and through `reviewComponentChange` with a tight budget (the tables survive `fitRelatedContext`, related code is trimmed first).

#### As built (2026-10-10)
Built as specified above; where the build differs or the spec was silent:
- **`PARSE_VERSION` 6 (2026-10-11).** "SQL in code" added `ddl` facts to the parse output without a bump, so a data folder that had run the first DB build (v1.21, `PARSE_VERSION` 5) kept serving cached facts with no DDL, and GraphReview's own schema stayed empty. `ANALYSIS_VERSION` 7 goes with it, so repos already analysed at 6 are re-analysed and their stored empty catalog is replaced. Any change to what `syntax/*.mjs` emits needs a bump, even before a release.
- **DDL in SQL tags; `PARSE_VERSION` 7 (2026-10-11).** A tagged template (`` sql`CREATE TABLE …` `` — Neon, `@vercel/postgres`, postgres.js, Drizzle's and Kysely's `sql`) was read as a query use and never as DDL, so a startup runner like MultiTool's `migrations/migrate.ts` (one `createX()` per table, `CREATE TABLE IF NOT EXISTS` then idempotent `ALTER … ADD COLUMN IF NOT EXISTS`) gave no database. DDL in a SQL tag now goes to the DDL reader like DDL passed to a call; MultiTool reads as one PostgreSQL database of 52 tables. The "no order between files" problem for loose DDL in several files is now raised only when one file changes a table another file creates, so a `CREATE TABLE IF NOT EXISTS` per action file reads cleanly. Smoke-tested: the Neon runner, Drizzle `db.execute(sql`…`)`, Kysely `` sql`…`.execute(db) ``, Python `cursor.execute`.
- **`.sql` by content; `PARSE_VERSION` 8, `ANALYSIS_VERSION` 8 (2026-10-11).** A Java repo kept its schema as `src/main/resources/sql/create-tables.sql` + `schema-changes.sql`, which gave nothing (only schema-named files were read). `sources/sql-files.ts` now classifies every loose `.sql` by its statements (`classifySql`: CREATE TABLEs ≥ change statements → schema; otherwise ALTER / DROP / RENAME / CREATE INDEX → changes; index, FK and PK statements count as schema-ish, so a pg_dump stays a schema file). One schema file and one change file in a folder are a pair, decided by a trial replay (`SchemaState.check`: `reflected` when what a statement does is already there, `conflict` when what it needs is missing; `IF [NOT] EXISTS` statements — now marked `guarded` on the ops — never clash): case A (all clean) is one migration set, the schema file then each change block; case B (all reflected) and mixed are the schema file then the blocks marked `historyOnly` (replay only records them in the tables' history), mixed with an order problem listing what didn't fit (`schema-changes.sql:2 adds email, which users already has (in create-tables.sql)`). Any other mix of schema and change files in one folder keeps the schema files as written with a problem saying the pairing is unknown. Change blocks come from the file's comment runs (`DbFileFacts.blocks`, the shape change behind `PARSE_VERSION` 8); block ids are `<file>#<n>`, named by their comment. Content-detected files skip test paths (`TEST_PATH`); schema-named ones don't. A `migrations` / `migrate` folder where **no** file name starts with a version is now read by content too (before: every file "order unknown"); a versioned folder is still a migration set. A `.sql` schema file joins another tool's migrations only when it shares their folder — djangoproject.com's `tracdb/trac.sql` (the Trac database's dump) is now its own 27-table database instead of being merged into Django's, and with two databases the repo-wide dialect hint comes after the SQL guess, so Django's dialect shows as guessed. **Appended statements:** a migration the base had whose head statements start with all of the base's is no longer "edited": the extra statements are a migration the PR adds (`<id>+<n>`), so the §5 hazards apply to a change log's grown last block and to a pinned `.sql` appended to.
- **Pinned source, as built (2026-10-11).** Stored in `kv` as `kv:db-source:<repoId>` (`lib/db/db-source.ts`, deleted with the repo). `analyzeRepoCommit` takes it (and keys its in-memory memo by it); the analysis job, the target-graph job and the review's analyses pass it; `analyzeTree` hands it to `buildDbSchema` as `pinned` with the tree's file list, which then builds only `pinned:<file>` (`pinnedBuild` in `catalog.ts`; the set is `strict`, so a clashing statement is opaque and listed). `DbSchema.pinned` says which file the catalog came from (`missing` when the commit lacks it); `DbSchema.candidates` (every analysis, auto or pinned) lists up to 60 files with schema statements; the db-schema route adds `pin` (the pin as chosen now, ahead of the catalog while its re-analysis runs). `lib/jobs/db-source.ts` lists the analysed commit's paths (`git ls-tree --name-only`, its own, not the Files view's route) and applies a change: write or clear the pin, `deleteTargetGraphsForRepo`, `enqueueAnalysis`. The PUT refuses paths outside the repo and files not in the analysed commit. UI: `DbSourcePicker` (candidates + search, "Use this file", "Use auto-detect") in the empty state — also with a diff selected, unless the diff has table changes — and behind "Change" / "Choose the source file…" on a source line under the toolbar; after a change the view polls the repo until its analysis finishes and re-reads the schema (`useDbSchema().reload`), showing "Re-reading the schema from <file>…" meanwhile. Verified in the running app (own dev server on :3100, `.next-dev-3100`, removed after) on a scratch Java repo whose schema moved to `src/test/resources`: empty state with both candidates, the search, pinning the test schema (canvas of its 2 tables), a ref comparison to a branch that appends a table and a `DROP COLUMN` to the pinned file (+1 table ~1, 1 destructive `drop-column` finding in the Schema chip and the left column), "Change" to the change-only file (three ALTERs listed as not modelled), "Use auto-detect" back to the empty state; "Choose the source file…" on an auto-detected repo. **Limits:** a pin is one file — a schema split over several files can't be pinned as one; a pin change while an analysis is already running is picked up only by the next analysis (the source line keeps saying "Re-reading…" until then); the candidate list doesn't include ORM model files without DDL (Drizzle `pgTable`, Django models).
- **Reading.** Code facts come from a new tree-sitter extractor in the parse worker, `lib/analysis/syntax/db.mjs` (TS/JS and Python, run by `extract.mjs`, cached as `SymbolFacts.db`): decorated TS classes (entities), classes with `up(queryRunner)` and the calls in it, module-level `pgTable`/`mysqlTable`/`sqliteTable`/`pgSchema().table`/`pgEnum` declarations, Python classes with their attributes, keywords and `Meta`, Alembic `revision`/`down_revision` and `Table(…)` assignments, `upgrade()`'s `op.*` and `batch_alter_table` calls, table uses (Prisma delegates, builder strings, SQL text), write-ish call lines and dialect hints. Values are kept as data (`DV`, a richer cousin of `routes.mjs`'s `Val`: call chains, numbers, booleans). Non-code files (`.sql`, `.prisma`, `meta/_journal.json`, `migration_lock.toml`) are read **in-process** by `lib/analysis/db/read.ts` (like the infra readers, not a `syntax/schema.mjs`) and cached by blob (`PARSE_VERSION:db-<reader>:<blob>`); a `.sql` file is stored already parsed into ops (only the up part of dbmate / goose files; `*.down.sql` and Flyway `U` files are skipped). Go, Java, Kotlin and Rust files get a **lexical scan for SQL literals** (`scanSqlLiterals`, cached as `CachedParse.dbCode`), so a plain-SQL Go service links its queries; leading `--` comments (sqlc's `-- name:`) don't stop a literal reading as SQL.
- **SQL reader** (`db/sql.ts`): statements split on `;` outside quotes, comments, `$tag$` bodies and trigger/procedure `BEGIN … END`; transaction control, `SET`, `COMMENT ON`, `GRANT` are dropped as noise; a `DO $$ BEGIN <ddl>; EXCEPTION … END $$` block (Drizzle's guarded FKs) yields the DDL inside when all of it parses. Views are tables marked `view`. Types are normalised (`character varying(50)` → `varchar(50)`, `int4` → `integer`, …) for display and comparison.
- **Every source becomes ops** (`DbOp`: createTable, addColumn, alterColumn, renameColumn, createIndex, addFk, createEnum, opaque, …), replayed by one engine (`db/replay.ts`, names case-insensitive, Postgres `public` = no schema); a declarative `schema.sql` goes through the same engine without a history. Resolvers: `sources/prisma.ts`, `drizzle.ts`, `typeorm.ts`, `django.ts`, `sqlalchemy.ts` (models + Alembic), `sql-files.ts`.
- **Databases:** one per migration set — Prisma `migrations/` folder, Drizzle out-folder, TypeORM migration folder, one `django` database for all apps, Alembic versions folder, each plain SQL folder. Declarative sources (Prisma schema, Drizzle tables, entities, models, schema files) join the nearest compatible set by tool family and shared path; a `schema.sql` joins the only migration set when there is exactly one (a dump of the same schema); otherwise a source makes its own database. Table ids are lower-cased.
- **Ordering:** Prisma by folder name; Drizzle by the journal (a `.sql` the journal doesn't list is a problem, not replayed); TypeORM by the 13-digit timestamp in the class name or file (none → problem, not replayed); Django by a topological sort of `dependencies` across apps (squashed `replaces` stand in for the replaced ones; a cycle's members aren't replayed; two leaves in one app are a problem, but replayed in dependency order); Alembic by `down_revision` (several heads or bases, missing parents, cycles are problems — heads are replayed in dependency order, since each branch's own order is known); plain SQL by version prefix (Flyway dotted versions, `R__` after them; files without a version are problems, not replayed; equal versions replay by name, flagged).
- **Model naming:** TypeORM `snake_case(Class)` unless `@Entity("x")`, join column `<relation>Id`, base classes' columns included, `nullable` false by default; Django `<app>_<model>`, FK `x_id`, implicit `id bigint`, abstract bases' fields, many-to-many join tables, `managed = False` models never drift and their migration ops are dropped; SQLAlchemy `__tablename__` with mixins, `Column` nullable unless the key, `mapped_column` / SQLModel nullability from the annotation; Python-side `default=` is shown as `… (in Python)`, not a database default.
- **Merging and drift:** the best source defines a table; lower sources add the columns and FKs it lacks (with their own source badge — a model field the migrations never created shows as a `model` column). Drift (`field-no-column`, `column-no-field`, `model-no-table`, `table-no-model` — the last only against a complete declarative schema: Prisma, Drizzle) is computed against the migrations, or the schema file when there are no migrations; tool bookkeeping tables (`_prisma_migrations`, `alembic_version`, …) are never "without a model". The comparison compares only each table's own-source columns, so a migration that drops a column the model still has shows as dropped (plus drift), not unchanged.
- **Links:** model uses come from the symbol graph's resolved uses of the model's declaration plus same-file references, and — for Python imports the resolver can't place (a package under `backend/` imported as `app.models`) — from `from <module> import <Model>` whose module path ends the model's file. Migration files never count as uses. Builder strings, like SQL text, are kept only when they name a known table. Each use carries its enclosing declaration; endpoint links follow the handler's range, its declaration and its reach (§6.11). `DbSchema.uses` is capped at 8,000; `endpointTables` maps endpoint → tables.
- **Findings** are synced as category `schema` beside `structure` and `infra` (`STATIC_FINDING_CATEGORIES`), stable ids from target + rule + table + column + migration, `componentId` the migration file's owner (folder fallback). Decisions where the spec was silent: `ALTER COLUMN … SET NOT NULL` on an existing nullable column without a default counts as `not-null-no-default`; a SQLite-style rebuild (`CREATE new_X; DROP X; ALTER new_X RENAME TO X` in one migration) isn't a drop or a rename — its lost columns are `drop-column` and its new NOT NULL columns `not-null-no-default`; FK-without-index is checked against the head's indexes, primary key and unique columns, for FKs the PR's migrations add only; `rename-table` / `rename-column` only from explicit renames (a removed and added table with equal columns is shown as renamed, never a finding). Postgres-only rules need the database's dialect to be Postgres (declared or guessed).
- **Review context:** `ReviewRelatedContext.tables` (`ReviewTable`: header, `+`/`−`/`~` column lines, notes — indexes, references, new enum values, drift, where this component uses it), rendered as "Tables this code touches" with the check-the-code instructions; the tables of a component are those its changed files use, model or migrate. Schema findings join the infra ones in "Already reported". `fitRelatedContext` keeps the tables: related code goes first, then unchanged tables, then neighbour descriptions, then the changed tables' unchanged columns (replaced by "… N unchanged columns"), then their notes. The intent check gets `describeSchemaChange` (`PrIntentInput.schema`). **Fixed on the way:** a migration the change *adds* isn't in the analysed graph, so it matched no component and was never reviewed; the review job now gives a new migration or schema file (one the head's catalog knows) to the component owning its nearest analysed folder. Other new files keep the old behaviour. Migration `.sql` and `.prisma` files a database is built from are now graph files (language `sql` / `prisma`, the App map's data layer).
- **UI:** `DataView` (canvas and list, `DataMode` remembered per browser), `DbTableDetail` (the explainer: in the right column from the canvas, in place in the list), `SchemaChangesSection`, `useDbSchema`, `db-view-model.ts`, `db-types.ts`. `CardFlow` gained `groups` — ELK compound nodes (`hierarchyHandling: INCLUDE_CHILDREN`, ROOT coordinates) drawn as dashed boxes behind their cards. A canvas shows at most 250 cards (then a note: search or use the list). "Changed only" rows are the head's table with the catalog's component, endpoints and usage. The PR map's `⛁N` counts tables a card's files use, model or migrate, plus the tables a migration the diff adds touches. The API explainer shows "touches …" with SQL-text-only links marked. - **SQL in code (the 7th v1 source, added 2026-10-10 after GraphReview itself showed 0 databases — its schema is `lib/db/schema.ts`'s `MIGRATIONS` array).** The parse records DDL literals apart from uses (`DbCodeFacts.ddl`): TS/JS and Python through `syntax/db.mjs` (a literal whose start — after whitespace and `--` / `/* */` comments — is CREATE / ALTER / DROP of TABLE, INDEX, TYPE or VIEW naming its object, `IF NOT EXISTS` included; an element of an array / list literal carries which array and its 1-based position), Go / Java / Kotlin / Rust through the lexical scan (the bracket a literal sits in stands for the array; a bracket with one DDL literal isn't one). A DDL literal is never a use, even inside `db.exec(…)`. `sources/sql-in-code.ts`: each array of ≥ 2 DDL literals is a migration set (tool `sql-in-code`, one migration per element, id `<file>#<n>`, shown as `lib/db/schema.ts #3` with its line); a file's other DDL literals are a declarative source replayed in line order (it joins the file's own array database when there is one); loose DDL in several files without an array is one database whose order between files is an order problem — each file is replayed on its own and a statement on another file's table stays not modelled. Statements with a template hole (`${…}`; Python f-string holes are kept the same way) are opaque. Skipped: test and fixture paths (`__tests__/`, `tests/`, `fixtures/`, `testdata/`, `e2e/`, `examples/`, `*.test.*`, `*.spec.*`, `smoke-test*`, `*_test.go|py`, `test_*.py`, `conftest.py`, `*Test(s).java|kt`) always — their DDL builds throwaway databases —, and files another tool already reads as migrations (a TypeORM migration's `queryRunner.query`, Alembic's `op.execute`, Django's `RunSQL`). The migrations file isn't a use (like every migration file). Dialect from the file's driver imports (`node:sqlite`, `better-sqlite3`, `sqlite3`, `pg`, `postgres`, `mysql2`, `psycopg`, `asyncpg`, Go drivers, …) or a `PRAGMA` literal → declared; else guessed from the SQL. Repo-wide dialect hints now say a database's dialect only when the repo has one database; with several they come after the guess from the SQL (marked guessed) — before, a SQLite driver import in one app made a Postgres migration folder elsewhere "sqlite". The UI labels such tables "migration (in code)" / "DDL in code" and the database line "migrations in code".
- **Edited migrations:** a migration the base already had whose statements the PR changes (compared without line numbers) is listed as `DbChange.edited` — a note in the left column ("edited"), in the intent check / chat / MCP text ("a database that already ran it never sees the edit"), never a finding and never a "migration the PR adds". An appended array element is a new id, so the §5 hazards apply to it. Inserting an element mid-array shifts the later ids: they show as edited plus one added.
- **Verified on GraphReview itself:** one database `sql-in-code:lib/db/schema.ts` (sqlite, declared by the `node:sqlite` import), migrations `lib/db/schema.ts #1`–`#5` (lines 18, 208, 230, 240, 250), 0 opaque statements, 26 tables with their columns (ai_providers, api_catalogs, app_maps, chat_messages, checklist_answers, checklist_items, component_deps, component_parents, components, db_schemas, file_imports, file_owners, files, findings, infra_catalogs, job_logs, jobs, kv, merge_suggestions, parse_cache, pr_changes, pr_maps, pull_requests, ref_snapshots, repos, target_graphs), SQL-text links from 21 files (20 in `lib/db/` plus `lib/jobs/runner.ts`), 50 of 57 endpoints linked; the smoke tests' fixture DDL is not a database. A review of `lib/db/finding.ts` gets findings, components and pull_requests as "Tables this code touches". taxonomy, saas-starter, the FastAPI template, simplebank, lireddit and djangoproject.com give the same catalogs as before (lireddit's TypeORM `queryRunner.query` DDL isn't double-counted).
- **Limits beyond the spec's:** DDL assembled at runtime (concatenation, a statement in a variable passed around) or kept in an array beside non-DDL elements counts by its literal only; the lexical scan's "array" is the enclosing bracket, so two DDL literals in one call's arguments read as an array; Python imports and Prisma delegates are matched by name (`prisma.order` → model `Order`); calls on instances (a repository object) aren't linked unless the model class is named; Django's `AlterModelOptions`/managers are ignored; MySQL `DELIMITER` scripts and SQL Server `GO` batches aren't split; Drizzle's `casing` option and column builders without a name use the property key; TypeORM many-to-many join tables aren't created from entities; third-party Django fields that add columns (django-money) show as drift.
