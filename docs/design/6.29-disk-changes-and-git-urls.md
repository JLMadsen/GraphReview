# 6.29 Changes on disk, any git URL, SSH clones

*Built 2026-10-19, from two user requests.*

## Changes on disk (local repos)

A local repo's diff picker has a **Changes on disk** entry above the modes,
and the same option in the Branches head list. It reviews everything not
yet committed (unstaged and staged edits, plus untracked files that
`.gitignore` doesn't exclude) against `HEAD`. The base can still be changed
in the Branches mode.

The whole pipeline works on commits, so the working tree becomes one. The
pseudo-ref `:worktree` (`WORKTREE_REF`, lib/jobs/git-ref.ts) is a valid
target ref (`:` can't appear in a branch name, so it collides with
nothing). Every ref-taking function in lib/jobs/local-git.ts passes it
through `localRev`, which calls `snapshotWorktree`:

1. Copy the repo's index to a scratch file, so `git add` only re-hashes
   files that changed.
2. Run `GIT_INDEX_FILE=<scratch> git add --all`, then `write-tree`.
3. `commit-tree` on top of HEAD, with a fixed identity and HEAD's own date.
   The same files therefore always give the same sha, and a review stays
   current until something on disk changes (§6.21 freshness then marks it
   stale). If nothing changed, the result is HEAD itself.

The user's branches, HEAD, index and files are never touched. The only
trace is unreferenced loose objects in `.git/objects`, which `git gc`
removes. This is the one exception to "local repos are only read" (§14),
chosen over a side repository with alternates, which would have needed a
second repo in every local-git path. A snapshot is reused for 3 s (memo
cache), so one request makes one snapshot.

Downstream, everything sees an ordinary commit sha: review pinning,
head-source reads, the target graph and the preview.

## One URL box, provider from the host

The add-repo dialog has two tabs: **Local path** and **Git URL**. The
GitHub and GitLab tabs are gone. `POST /api/repos` takes
`{ provider: "url", url }` (`"github"`/`"gitlab"` still work) and
`providerForUrl` decides by host:

| Host | Provider | What works |
|---|---|---|
| a server with a saved GitHub token (§6.30), `GITHUB_WEB_URL`'s host, github.com | `github` | as before: PRs, CI, posting |
| a server with a saved GitLab token, `GITLAB_WEB_URL`'s host, gitlab.com | `gitlab` | as before |
| anything else | `git` (new) | graph, branches, commits, ref comparisons, reviews. No PR list, CI or posting, and no API is probed. |

A `git` repo stores the URL as entered and must be reachable when added
(`probeRemote`). A typo or a key without access fails in the dialog with
the message a clone would give, not later as a failed analysis. Only
`http(s)://`, `ssh://`, `git://` and `user@host:path` are accepted
(`isCloneableUrl`). Local paths, `file://` and `ext::` are refused.

### The plain-git clone mirrors the server's branches

A `git` repo's clone (`<data>/repos/<id>`) uses the fetch refspec
`+refs/heads/*:refs/heads/*` and keeps HEAD detached at the default branch
(`syncGitMirror`). Every server branch is then a branch of the clone, so
the clone is read **in place** exactly like a local folder:

- `inPlacePath(repo)` gives the folder the local-git layer reads: the
  local path, or the `git` repo's clone.
- `readsInPlace(repo)` replaces the old `provider === "local"` checks
  wherever "no host API, ask git" was meant (diff, changed files, branch
  and commit pickers, file reads, CI, PR targets refused).

The branch and commit pickers and ref reviews fetch first through
`refreshGitMirror`, at most every 30 s. That way a branch pushed since the
last analysis shows up.

## SSH clones with the user's key

An SSH URL (`git@host:path`, `ssh://…`) clones with the user's own SSH
setup: keys in `~/.ssh`, `ssh-agent` and `~/.ssh/config`. Background jobs
can't answer prompts, so `GIT_SSH_COMMAND` is set once to the user's ssh
command plus `-o BatchMode=yes -o StrictHostKeyChecking=accept-new`. The
user's ssh command is their `GIT_SSH_COMMAND`, else `core.sshCommand`
(often the Windows OpenSSH, for its agent), else `ssh`.

- A host seen for the first time is trusted and added to `known_hosts`. A
  host whose key **changed** still fails.
- A key with a passphrase works only through the agent.
- PuTTY's `GIT_SSH` is left alone, since it takes no `-o`.
- simple-git passes the variable only when it is allow-listed with
  `allowUnsafeSshCommand`.

A GitHub/GitLab repo added by its SSH URL keeps that URL as `cloneUrl`. It
clones over SSH, while PRs and CI still use the server's token from Settings. Over
HTTPS nothing changes: the token saved for the server (§6.30) only,
never the user's credential helpers.

The SSH failures users can fix (key refused, missing agent, changed host
key) get their own messages (`withFriendlyAuthError`).
