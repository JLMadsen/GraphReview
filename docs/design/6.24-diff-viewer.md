# 6.24 The diff viewer: split view, whitespace, word marks, moved code and the all-files reader

*Built 2026-10-17.*

The file viewer's Diff tab used to be a unified diff of whatever patch the
host sent, and the review dock's Files tab was only a list. This section
upgrades both.

## Where the diff comes from

`lib/jobs/diff-files.ts` (`loadTargetDiff`) serves the viewer — the single
file route `GET /api/repos/[repoId]/diff-impact/file` and the new
`GET /api/repos/[repoId]/diff-impact/files` (every file at once).

- **Git first.** A local repo is diffed in its checkout. A hosted repo is
  diffed in the app's clone when the analysis already made one: the two ends
  come from the host (one call for a PR) and are fetched into the clone by
  `ensureCommitsInCache` if missing. A clone is never *made* in a request.
- **API only as fallback** — no clone, no fetch, or git failed. GitHub's
  `patch` leaves big files out and stops at 3000 files; the viewer says
  "from the host's API" when that is the source.
- Git runs with `--find-renames` (the review pipeline keeps
  `listLocalFilePatches` and its `--no-renames`, which suits the component
  graph). One combined `git diff` is split per file by its new-side path.
- Each file carries its head blob id (`--raw`) as its `fingerprint`.
- Caps: 1 MB of patch per file, 40 MB in all; past that the file says
  "cut off".

`preferLocalDiff` holds the preference itself, with the sources passed in,
so the smoke test checks it without a host.

## Whitespace

`?w=1` asks for whitespace-only changes to be left out. With git that is
`git diff -w`; a file with nothing else changed comes back
`whitespaceOnly`. An API patch comes back as is with `whitespace: "client"`
and the viewer filters it (`ignoreWhitespaceHunks`): inside each change
block, removed and added lines equal once whitespace is removed become one
context line (the new text), and hunks with no change left are dropped.

## What the viewer draws (`components/graph/diff-model.ts`, `DiffViewer.tsx`)

- **Unified or split.** Split puts each change block's removed and added
  lines side by side (positional pairing, as GitHub does) and wraps long
  lines. The +/− column stays in both layouts, so add/remove never rests on
  colour alone.
- **Word marks.** Each paired removed/added line is word-diffed (tokens:
  words, runs of whitespace, single punctuation; LCS). Pairs sharing under
  40% of their characters, or longer than 400 tokens, get no marks — noise.
  Marks are `<mark class="diff-word">` spliced into the syntax-highlighted
  HTML (`markRanges`), tinted *and* underlined.
- **Moved code.** An equivalent of `git diff --color-moved` on the parsed
  hunks, across every file shown: consecutive added lines matching
  consecutive removed lines elsewhere (trimmed text), at least 20 letters and
  digits per block (git's threshold). A remove and add in the same change
  block is an edit, not a move. A moved block gets a "Moved from / to
  path:line" row above it and its own tint; screen readers hear "moved".
  Working on hunks rather than `--color-moved` output means API patches get
  it too.

## Toolbar and keys

`DiffToolbar`: Unified / Split and Hide whitespace, as buttons with
`aria-pressed`. Each viewer (`modal`, `reader`) remembers its own choice in
localStorage (`graphreview.diff.<viewer>.layout|ignoreWhitespace`). Keys
while open and not typing: `S` split, `W` whitespace.

## The all-files reader (`AllFilesReader.tsx`)

Opened from the Files tab ("Read all diffs") or from a file's diff in the
file viewer ("All files"). One scrolling column of every file, each with a
sticky header (status, old → new path, counts, **Viewed** checkbox); a file
list on the left with ✓ marks and "n of N viewed · m to go".

- `J` / `K` next / previous file, `V` marks the current file viewed and
  moves on; viewed files fold away (the chevron opens them again).
- Viewed is kept per diff (`graphreview.viewed.<repoId>.<target key>`) as
  `path → fingerprint`: the head blob id, or for an API patch a hash of the
  patch. It clears exactly when a push changes that file and survives
  pushes that don't.
- Opened from a finding, it starts at that file with the finding's lines
  ringed and scrolled to, like the single-file viewer.
- File bodies render when they come near the viewport, so a PR of thousands
  of files stays usable.
