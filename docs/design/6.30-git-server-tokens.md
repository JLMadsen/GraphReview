# 6.30 Git servers: one token per server

*Built 2026-10-19.*

Settings used to have a GitHub PAT field and a GitLab PAT field. A token,
though, belongs to a **server**, not to a provider:

- github.com and a GitHub Enterprise server need different tokens.
- Two GitLab instances need different tokens.
- A plain git server (§6.29) had nowhere to put one.

The fields are replaced by one **Git servers** list.

## The card

Each row shows a server (`git.example.com`), what it is (GitHub · login,
GitLab · username, or "Git server — HTTPS clones only") and an × to remove
its token. The token itself never comes back to the browser.

To add one, the user enters the server (or any repo URL on it), the token,
and optionally a username. A second token for the same server replaces the
first. The scope help is folded under "Which scopes?". If no token is
saved yet, the server field starts as `https://github.com`.

## What a server is: asked once, on save

`probeGitServer` (lib/jobs/git-server-probe.ts) calls `GET <api>/user` with
the token:

1. The GitHub API: api.github.com for github.com, else
   `<origin>/api/v3`, or `GITHUB_API_URL` when the server is
   `GITHUB_WEB_URL`.
2. The GitLab API: `<origin>/api/v4`, or `GITLAB_API_URL`.

The order follows the token prefix (`glpat-` tries GitLab first) and the
built-in hosts. The first API that answers with a user sets the kind, the
API URL and the username.

- If a GitHub/GitLab API answers 401/403, the token is wrong and nothing is
  saved.
- If neither API exists, the server is a plain git server (`kind: "git"`),
  and its token is only used for HTTPS clones.

## Storage and migration

The list is kept at kv key `git-tokens` (lib/db/git-tokens.ts):
`{ id, origin, kind, apiUrl?, username?, tokenEncrypted, addedAt }`,
encrypted like every other secret.

On the first read, the old `githubPatEncrypted` / `gitlabPatEncrypted`
settings move into it. Each is filed under `GITHUB_WEB_URL` /
`GITLAB_WEB_URL` (else github.com / gitlab.com) with the matching API env
var, and the old fields are deleted.

## Picking the token: by host

lib/jobs/git-hosts.ts answers "which server is this URL on, and what is its
token?". It matches on host name alone, so `git@host:path` finds the token
saved for `https://host`. A server is known from, first match first:

1. a saved token, which recorded the server's kind;
2. the `*_WEB_URL` env overrides;
3. github.com and gitlab.com.

Each part uses this:

- **API calls.** lib/github and lib/gitlab take `GitHostAuth`
  (`{ token, apiUrl? }`) instead of a bare token, so each call goes to the
  token's own server. Unset `apiUrl` falls back to the env override, then
  the public API.
  - `GitHubRepoRef` / `GitLabProjectRef` now carry their `origin`, and
    clone/web URLs are built from it rather than from `*_WEB_URL`.
  - `resolveGitHubAccess` takes the token of the repo's own server.
- **Clones.** `authEnv(url)` (lib/jobs/source.ts) sends the server's token
  as before, for HTTPS URLs only. The Basic-auth username is
  `x-access-token` for GitHub, `oauth2` for GitLab, and the saved username
  (else `git`) for a plain git server; Bitbucket needs the real username.
  SSH URLs never send a token.
- **Adding a repo.** `providerForUrl` asks the same registry. A server that
  a GitLab token was saved for is GitLab, without any env var.

The env vars still work as defaults and for a proxied API. They are no
longer needed for an ordinary self-hosted GitLab or GitHub Enterprise
server.
